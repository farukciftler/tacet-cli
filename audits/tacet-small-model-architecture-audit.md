# Tacet — Small-Model Architecture Audit Report

**Subtitle:** An architecture audit and improvement roadmap for Apple FoundationModels (~3B parameters, ~4096-token context) small-model fitness

**Project:** Tacet (repo/target: `Tacet`) — a fully on-device, offline iOS assistant
**Date:** 19 July 2026
**Scope:** The whole code base (84 Swift files, ~17,100 lines) — 9 architectural dimensions
**Note:** This audit is review + report only; **no code was changed.**

---

## 0. Method

The audit was run as a parallel multi-agent workflow split **by architectural dimension**, not by file ownership:

- **9 independent auditor agents** ran concurrently; each examined one dimension (prompt/token budget, intent profile & tool budget, tool schemas, MCP bridge, skill/guidance injection, structured-output parsing, bulk data offload, error/retry/cancellation, evaluation & self-test) in read-only mode.
- Every finding was tied to `file:line` evidence and to a concrete **small-model impact**.
- A **synthesis agent** merged the structural findings of the 9 dimensions, resolved contradictions, and collected the recommendations into a single roadmap as P0/P1/P2.
- Total: **10 agents, 0 errors, ~707,000 tokens, 161 tool calls.**

The axis of assessment was held fixed across every dimension: *token budget, prompt length, tool count/schema complexity, output-parsing fragility, hallucination surface, deterministic guarantees.*

# Tacet Architecture Audit Report — ~3B / 4096-Token FoundationModels Fitness

## 1. Executive Summary

Tacet's core philosophy — "build a deterministic scaffold and confine the small model to as narrow a decision space as possible" — is an above-class design that answers small-model reality correctly: the tool SET is chosen by code, not by the model (ModelService.swift:527-556), the token budget is managed by real `tokenCount` rather than estimation (ModelService.swift:901-908), bulk data is carried over DataStore without passing through the model (TacetTool.swift:41), code/HTML output is verified deterministically (CodeEngine.swift:96-98, PageVerifier.swift). The audit does, however, reveal a consistent crack pattern: **a deterministic guarantee is established in one layer and then handed back to the model/prompt in the next.** The three most critical levers: (1) because the fixed prompt cost is ~4-5× what is documented (~2100-2400 tokens, half of 4096), the conversation window is exhausted before it even begins (Router.swift:5 vs :25-64); (2) discriminator/format fields being plain `String` instead of real enums, carrying the reference across turns being left to the prompt, and remote MCP writes falling outside retry protection produce **silent data loss and double external side effects** in exactly the small model's most likely deviations (CalendarTool.swift:30, CreateDocumentTool.swift:46-54, MCPTool.swift:227-235); (3) the real-model tests that measure the model's genuinely fragile behaviour (language anchor, argument correctness, format compliance) are not bound to any automatic gate (Evaluation.swift:190-192) — meaning every fix above is unprotected against regression. In short: the backbone is sound, the fragility is at the backbone's ends.

## 2. Overall Architectural Assessment

The design's core claim — "because a small model is prone to hallucination and to fragile tool calls, surround it with deterministic shells" — has been applied consistently and **actually works** in most places. Where it is strong is every point at which the decision is TAKEN AWAY from the model: tool set selection (ModelService.swift:527-556), the tool count cap (6-8, applied before translation, ModelService.swift:1037), reading the next-turn signal from the chip icon rather than from the model's text (ModelService.swift:590-593), keeping the approval gate in code and never leaking a flag to the model (ToolExecutor.swift:50-53), and structurally hiding bulk data from the model through the `returnedToModel`/`rawOutput` split (TacetTool.swift:41). These are guarantees resting on code, not on the small model's "good intentions".

The crack opens where the decision is HANDED BACK to the model or the prompt, and it follows a surprisingly repetitive pattern:

- **The deterministic infrastructure exists but the last step falls back to text:** tool failure is knowable in the executor yet returns to the model as an English sentinel string (TacetTool.swift:51), retry safety trusts a single `String` state report (`.written`) (ToolExecutor.swift:163), table structure is bound to one rigid form (Table.swift:63-65).
- **Layers do not know each other:** skill injection is unaware of the active profile's tool set (SkillStore.swift:64), two parallel keyword systems (profile traces vs skill triggers) are synchronised by hand (ModelService.swift:596-657 vs the `triggers` in the .md).
- **The mechanism is built but not wired into production/protection:** core skill truncation is silent (SkillStore.swift:78-85), ref-miss is a silent success (CreateDocumentTool.swift:78-87), the real-model eval writes to a file without a threshold (Evaluation.swift:190-192).

So the architecture was designed with the right instincts for a small model, but because the LAST MILE of that instinct is not closed deterministically, the guarantees drop out at exactly the edge cases where the most fragile model will fall most often.

## 3. Findings Dimension by Dimension

### 3.1 Prompt construction & token budget
**Current state:** Progressive disclosure is real (skills are not embedded in the instruction, a single skill is attached once — ModelService.swift:344-409), the budget is managed at an 80% threshold using real `tokenCount` (ModelService.swift:904), the summary is produced in a separate session (ModelService.swift:928-930), raw tool output is not carried into history (ModelService.swift:942-958). The infrastructure is above class.
**Most severe weaknesses:**
- The fixed cost is ~4-5× what is claimed: `instructionsEN` says "~150 tokens" (Router.swift:5) but the block is 2833 characters ≈ ~650-700 tokens; on top of that a non-EN language anchor ~200 tokens (ModelService.swift:434-445) + 8 tool schemas ~1200-1500 tokens = for a Turkish user **~2100-2400 tokens, ~50-60% of 4096** is consumed before the chat starts. Design decisions (the summarisation threshold, the preserved turn) may have been tuned on a wrong assumption.
- Off-profile permanent blocks are paid for in every profile: the SEARCH RESULTS paragraph (Router.swift:44-50) and the document-export flow (Router.swift:57-60) are in the fixed instruction, whereas the everyday profile has no web_search tool (ModelService.swift:280-290) — expecting a tool that does not exist creates a hallucination surface.
- The reply language is reinforced in three separate places (Router.swift:29-32 + ModelService.swift:434-445 + :404), ~350+ tokens for a single concern, re-paid on every session setup.
**Recommendation:** Split the instruction into a short language/tool-neutral CORE + a profile-specific appendix; bring the core down to ~250-300 tokens and move the detail into the skill layer; drop language reinforcement to the nearest channel (a turn-leading `[Reply in X]`).

### 3.2 Intent profile & tool budget
**Current state:** The tool set is deterministic, the 6-8 cap is actually enforced, the next-turn signal comes from the chip icon (closed to hallucination, ModelService.swift:587-593). The right backbone.
**Most severe weaknesses:**
- First-match-wins kills the cross signal: "turn my notes into excel" first catches on "my notes" in `everydayTraces` and falls into the everyday profile (ModelService.swift:539), and that profile has NO create_document (:289) → the user's explicit file request silently disappears.
- There is no in-turn recovery from a wrong profile (ModelService.swift:527-556): if the picker is wrong, the needed tool is simply not in the session and the model invents success — no deterministic guarantee is in play at all.
- everyday/document sit exactly at the cap with 8 tools; the code's own comment admits the cap is "being strained" (ModelService.swift:276-279). Watch/Code are rare but add discrimination load on every turn.
- Operation arguments are free `String` + fuzzy `.contains` (see 3.3).
**Recommendation:** Add an in-turn wrong-profile recovery gate (P0); move profile selection to signal scoring; bring everyday down to 6 tools and take Watch/Code into a separate profile; soften the attached-document lock on a strong non-document signal.

### 3.3 Tool schemas & descriptions (@Generable/@Guide)
**Current state:** Constrained decoding is in place, the model is not made to parse free text (TacetTool.swift:6-7); most tools take a single required string (Calc/Contact/Search/WebSearch) — ideal for a small model. MCP enums are translated into a real constrained list (MCPTool.swift:406-412).
**Most severe weaknesses:**
- **Native discriminator/format fields are not real enums but plain `String` + fuzzy matching:** `var action: String` + `arguments.action.lowercased().contains("add")` (CalendarTool.swift:19-30); when the model produces `action="add"` in an English turn the native literal is not found, and the code SILENTLY falls through to reading — the user sees a list while trying to add an event (ReminderTool.swift:185-186, TimeTool.swift:21 have the same pattern). With a @Generable enum the framework forces a valid case and this entire class disappears.
- The create_document schema: a hand-aligned markdown table INSIDE a JSON string + the mutual exclusion of `content`/`sourceRef` stated only in prose (CreateDocumentTool.swift:30-32) — a risk of a broken Excel or an empty document.
- Native/English language mixing: field names native, values native, descriptions English, mixed within a single enum ('text' vs 'markdown', CreateDocumentTool.swift:24) — exactly the point where a 3B model stumbles on cross-language mapping.
- The run_code `language` field is dead but is still a required decode slot (RunCodeTool.swift:42-44, :70).
**Recommendation:** Convert discriminator/format fields to @Generable enums (P0); remove the dead `language` field; moving to enums solves the language mixing at the root; put a length cap on MCP per-property descriptions too (MCPTool.swift:389 currently passes them raw).

### 3.4 MCP bridge & dynamic tool load
**Current state:** A four-layer cap is applied before translation (200→6, ModelService.swift:1037), a single connection is selected, definitions are summarised on-device and cached (ConnectionService.swift:309-327), a depth limit of 4 + rejection of anyOf/$ref (MCPTool.swift:327,368). The defence is well built.
**Most severe weaknesses:**
- **Schema WIDTH is not limited at all, only depth:** a depth-1 but 40-field single `object` passes the limit and enters the model as-is (MCPTool.swift:380-393); even with a "6 tools" cap, each tool can be a token bomb in width, and a 3B model cannot fill 40 fields correctly.
- The 6-tool budget is filled blindly by the server's `tools/list` order rather than by relevance (ModelService.swift:1037): if the needed tool is 7th in the list it is NEVER visible to the model — the most expensive resource is spent at random.
- Tool name collisions are not resolved; the code does not keep the "may have taken a prefix" promise of line 129 (MCPTool.swift:276-282) — "get-user"+"get_user" can both descend to "get_user" and drop the profile.
- The cap is not applied on import: up to 200 tools are all summarised on-device one by one (ConnectionService.swift:274-280) while only 6 are used — minutes of background inference.
- English imperatives embedded in tool output (see the crossing theme, 3.8).
**Recommendation:** Add a field/node budget for schema width; fill the 6-tool slot by relevance using light text matching + a `lastUse` signal; resolve name collisions with dedup+prefix; bound summarisation with the cap+relevance too.

### 3.5 Skill/guidance injection
**Current state:** A single skill is injected once, not into the system instruction but into the turn's prompt and immediately before the question (ModelService.swift:382-389) — the right choice, exploiting last-block weight; length-weighted scoring resolves genuine ambiguity (SkillStore.swift:64-74).
**Most severe weaknesses:**
- **The 700-character blind truncation throws away the two most valuable parts (CRITICAL):** SkillStore.swift:78-85 cuts the body from the end; measurement: at code.md 1069→690, `## Example` (the run_code example) AND `## Rules` ("Never claim you ran code without a successful tool call") drop entirely; at web-page.md 1248→683 the example+rules drop; at create-document.md the "NEVER compute totals yourself" =SUM rule drops. So the skill ends up producing exactly the hallucination it was trying to solve (invented results, totals off the top of the head).
- Substring matching (no word boundary): 'find' ∈ 'findings' → a weather question wins the search skill, 'read' ∈ 'ready' → read-document (SkillStore.swift:68); the wrong guide locks the small model into the wrong behaviour.
- Injection is unaware of the active profile's tool set: 'calculate dollars with python' → profile=.search (no run_code) but the skill says "Call run_code" (ModelService.swift:320-325 vs SkillStore.swift:64) — an out-of-schema call.
- Two parallel, hand-synchronised lists (profile traces vs .md triggers) can drift.
**Recommendation:** Convert blind truncation into a "core-first" model — example+critical rule at the head of the body, injection takes only the core (P0); make trigger matching word-bounded, short triggers exact-only (P0); cross the skill with the profile tool set; derive from a single trigger source.

### 3.6 Structured output & parsing fragility
**Current state:** Half-finished tables are not rendered while streaming (TacetReply.swift:147-152), the code sandbox is deterministic (CodeEngine.swift:96-98, a cap of 2 executions), HTML is verified off-screen (CreateDocumentTool.swift:65-77). Strong deterministic guarantees.
**Most severe weaknesses:**
- The table detection gate is too strict: it requires the triple of outer pipe + separator row + data row (Table.swift:63-65); a 3B model frequently produces tables without outer pipes ('Coffee | Price') or without a separator → the gate does not open and the user sees raw `| a | b |`. The format pressure (Router.swift:40) says "print the rows" while the parser accepts one rigid form — the instruction and the tolerance contradict each other.
- **A broken table on the Excel path → single-column garbage xlsx (silent structural loss):** if `fromMarkdown` returns nil the raw text is poured into a single column (EditDocumentTool.swift:46-50, ExcelEngine.swift:25-28), and the user sees an "edited" chip and finds a broken file — a false success signal.
- A half/broken table is a silent LOSS: if `fromMarkdown` is nil the collected pipe rows are skipped without being added anywhere, there is no else branch (TacetReply.swift:195-202).
- create_document takes only the first table and drops the rest (CreateDocumentTool.swift:49-53).
- There is no broken-output test; the parser contract is tested only with flawless markdown (SelfTest.swift:87-94).
**Recommendation:** One tolerant parser (separator optional, outer pipe optional) + on nil never drop the pipe rows, add them back as `.text` (P0); put a broken table on the Excel path into a correction loop like the HTML pattern; preserve multiple tables + surrounding text; add a broken-output test matrix.

### 3.7 Bulk data offload & the 4096 bypass (DataStore + sourceRef)
**Current state:** The channel split is deterministic and in a single place (TacetTool.swift:41); the reference generator is monotonic, `clear()` does not reset the counter (DataStore.swift:40-48) — an old-ref collision is structurally closed; `get()` is tolerant (it trims quotes/spaces). Solidly built.
**Most severe weaknesses:**
- **If sourceRef cannot be resolved, SILENT success (CRITICAL):** if `get(ref)` returns nil the branch is skipped, execution continues with `body = arguments.content` (the model was told to leave content empty when it uses a ref) and returns `file_created` in any case (CreateDocumentTool.swift:46-54, 78-87). The user gets an EMPTY/incomplete Excel and hears "Ready" — hard-to-diagnose data loss.
- The reference label is inconsistent: source tools show the model `data_ref=` (CalendarTool.swift:73) but the argument name is `sourceRef`, and MCP says `sourceRef=` (ConnectionService.swift:434); a weak model can write the whole `data_ref=calendar-1` string into the argument, `get()` does not strip the `data_ref=` prefix → no match → the silent success above.
- The ref chain is multi-step and 10 real rows sit in the preview: instead of carrying the ref, the model tends to write the 10 rows it can see straight into `content` (CalendarTool.swift:124-126) → an Excel that "looks fine" with 10 rows out of a 200-record calendar; the offload pattern is toppled at its very reason for existing.
- read_document is outside the offload: it dumps ~375+ tokens straight into context (ReadDocumentTool.swift:43-44).
**Recommendation:** If the ref cannot be resolved NEVER produce silently — an explicit error branch, and widen `get()`'s tolerance to strip the `data_ref=`/`sourceRef=` prefixes (P0); a single opaque ref token with a label identical to the argument name (P0); suppress the preview on an export intent or reduce it to a single step; bring read_document into the ref channel too.

### 3.8 Error/retry/cancellation semantics
**Current state:** Errors are read in the UI as a flag rather than as text (ModelService.swift:41-53), cancellation is not counted as an error and preserves `streamingText` (:891-894), `generationNo`+a defer guard protects the new turn's flag (:700,757), the local write retry lock is correct (:817-821). Flag-based and sound.
**Most severe weaknesses:**
- **Remote MCP writes are OUTSIDE retry safety — a double external side effect (CRITICAL):** MCPTool deliberately reports `.read` (:227-235), only `.written` sets `worldChanged` (ToolExecutor.swift:163); if a model error occurs after a remote "open issue" has returned successfully, `recoverFromError` sees `worldChanged==false` and resends the same prompt → a duplicate Jira issue, and with `retryable=true` even a third-copy gate opens. The asymmetry: the same `.read` dirties the approval gate (`sessionDirty`) but not the retry gate.
- `recoverFromError` carries no cancellation/`generationNo` protection: in a 'stop'+new-request scenario the old turn's recovery starts a new generation in the background while `generating=false` and races the session against the new turn (ModelService.swift:836,849) — invisible battery burn + session corruption.
- The tool→model error contract rests entirely on an English sentinel (`tool_failed:`, TacetTool.swift:51; `remote_tool_error:`, ToolExecutor.swift:1092-1099); `isError` still stays FALSE, and the model either echoes the sentinel or ignores it and says "I added it".
- There is no deterministic cross-check between the "I did it" claim and a real tool call (`worldChanged`/`traces`) (Router.swift:39 is instruction only).
**Recommendation:** A separate `mayHaveSideEffect` flag for remote side effects + widen the retry gate (P0); bind `recoverFromError` to the turn id — a cancelled turn must not run recovery (P0); derive tool failure from the structural `.failed`, and let the UI decision come from the flag; model the side-effect type separately from the state enum.

### 3.9 Evaluation & self-test coverage
**Current state:** Deterministic fences are asserted generously (SelfTestCases.swift:96-205, 673-762: memory filters, deduplication, injection budget, approval gate, network monopoly); tool verification rests on the chip trace rather than the model's narration (ToolTrace.swift:29-53); the memory block's "false positive=fail, miss=warning" distinction suits small-model reality (Evaluation.swift:203-231).
**Most severe weaknesses:**
- **Real-model behaviour tests are not bound to any automatic gate (CRITICAL):** Evaluation writes the result to a file and calls `print`, with no threshold/exit (:190-192); LanguageTest is the same (:126); there is no XCTest target/CI. This is exactly the "the mechanism gets built but never wired into production" regression pattern — if tool selection/language/format regresses on a prompt change, no build breaks.
- Nondeterminism is not suppressed: `streamResponse(to: question)` takes no options, there is no GenerationOptions/temperature (ModelService.swift:867); one run per case (Evaluation.swift:119-123) → real regression and sampling noise cannot be separated.
- The language anchor is not measured automatically, it is left "to the eye" (LanguageTest.swift:113-115) — the small model's signature error is not measured.
- Argument correctness is almost never exercised, only "was the tool called": the calc cases do not verify the 1000/135/200 result (Evaluation.swift:43-45), calendar-add only counts the icon.
- Weak assertions produce false greens: time-clock `replyMustContain: ":"` (every reply passes); the dead `currentTime()` (:544 defined, never called).
**Recommendation:** Bind the model-behaviour eval to a CI gate with a threshold, an exit code, and FAKE fixtures (P0); lowest temperature + an N-run majority ratio per case (P0); assert the language anchor automatically with NLLanguageRecognizer; exercise argument correctness through `rawInput`/`rawOutput`; tighten the weak assertions.

## 5. Crossing Themes & Risks

1. **The deterministic infrastructure exists, but the last mile is left to text/the prompt.** The service→UI error path is flag-based (correct), but the tool→model path is an English sentinel string (TacetTool.swift:51, ToolExecutor.swift:1092-1099); the tool set is chosen deterministically but the operation argument is a plain `String` (CalendarTool.swift:30); the offload channel is deterministic but carrying the reference is left to the prompt (Router.swift:57). **The root fix is shared: move to a constrained/structural channel everywhere the decision can be taken away from the model** — P0-4 (enums) on its own closes the finding that repeats across 3.2/3.3/3.6.

2. **The fixed token cost has been systematically under-computed.** The "~150 tokens" comment is in reality ~700 (Router.swift:5), so ~2100-2400 tokens of the window are gone before it starts; language reinforcement is in three places, and the ISO-8601 directive is repeated across CalendarTool/ReminderTool (CalendarTool.swift:21, ReminderTool.swift:180). This accelerates early summarisation and creates "invisible forgetting". Risk: any other tuning done before the fixed cost is fixed (threshold, preserved turns) rests on a wrong assumption.

3. **Silent success = the most expensive error class, and it repeats across several dimensions.** Ref-miss empty document "file_created" (3.7), broken table garbage xlsx "edited" (3.6), remote write retry duplicate issue (3.8), "I added it" without ever calling a tool (3.8) — in every case the system holds a deterministic signal (`worldChanged`, `get()==nil`, `fromMarkdown==nil`, `traces`) and does not turn it into an error/correction. Because a small model cannot produce these signals by itself, catching them on the code side is mandatory.

4. **The "a mechanism not wired into production/protection" regression pattern.** This pattern, also named in the memo, is clearest in 3.9: the real-model eval runs but breaks no gate (Evaluation.swift:190-192); on top of that skill truncation is silent, ref-miss is silent, and the name-collision promise is not kept. **Without P0-5 the durability of the other four P0s is not guaranteed** — which is why the eval gate stayed on the list.

5. **Disconnection between layers produces drift.** Two parallel keyword systems (profile traces vs skill triggers, ModelService.swift:596-657 vs the .md files), profile-independent skill injection, and piling both retry safety and the visual-state axis onto the single `.written` flag — all of these require manual synchronisation and, when they slip at one point, leak straight into small-model behaviour.

## 6. Closing Verdict

Tacet has built the right backbone for working with a ~3B/4096-token model: taking the decision away from the model, real token measurement, deterministic offload and verification instincts are all in place and mostly working. The architecture's small-model fitness breaks not in the design's philosophy but in the places where the last mile of that philosophy is handed off — the fixed prompt cost silently inflating, decisions such as `String` discriminators/ref-carrying/remote-writes being left to the prompt, and real-model behaviour being bound to no gate at all. The common denominator of the five P0s is simple and low-risk: **bind every silent-success path to a deterministic catch, bind every free-text decision to a constrained channel, and lock these fixes down with a thresholded eval gate.** These five moves make the small model's most likely deviations visible and correctable without disturbing the solid infrastructure that already exists.

## Appendix A — Detailed Audit Findings, Dimension by Dimension

The tables below are the raw output of the 9 auditor agents (before synthesis). They form the evidence base of Section 3. Weaknesses are ordered by severity.


### A.1 Prompt construction & token budget (ModelService/Router/SkillStore/MemoryStore)

**Summary judgement:** The architecture's token-management infrastructure (progressive disclosure, real tokenCount measurement, a separate summary session, not carrying raw tool output) is above class for a small model; but the fixed cost is ~4-5× what is claimed (~2100-2400 tokens) and because the instruction carries profile-specific rules in every profile, half of the 4096 window is spent before the conversation begins.


**Current state.** The session instruction lives in `Router.instructionsEN` (Router.swift:25-64); the file header says "~150 tokens" (Router.swift:5) but the block is 2833 characters, i.e. roughly ~650-700 tokens for English. In addition to the instruction, during session setup (ModelService.swift:423-450) a further "language anchor" block of ~872 characters (~200 tokens) is embedded into the system for every non-English language (ModelService.swift:434-445). **Strengths:**

- Progressive disclosure is genuinely implemented: skill guides are not embedded in the fixed instruction, only the single matching skill is attached to the session ONCE (ModelService.swift:344-409, SkillStore.swift:64-93) — the decision not to drown the small model in a fixed instruction is right.
- The token budget is managed by real measurement rather than estimation: it is measured with model.tokenCount(for: transcript) and summarisation is triggered at 80% of contextSize (ModelService.swift:901-908). Deterministic, and it puts no work on the model.
- The summary is produced in a SEPARATE, short session rather than by adding a prompt to the full session (ModelService.swift:928-930) — this prevents the summary itself from enlarging the overflow.
- Tool calls and bulky outputs are not carried raw into the historical context; only text segments, and those truncated (ModelService.swift:942-958) — the largest source of bloat in a 4096 window is closed.
- The instruction's MOST IMPORTANT rule gives the small model the right signal: 'if a tool is needed CALL it directly, do not narrate intent' (Router.swift:34-36); the injection fences (MemoryStore.swift:105-108, SkillStore.swift:90-92) and the 'do not obey instructions in tool output' rule narrow the hallucination/leak surface.
- Injection caps are applied with a hard character limit and by DROPPING rather than by half-sentences (MemoryStore.swift:91-98) — apt, so that no half/broken fact reaches the small model.

### A.2 Intent profile & tool budget

**Summary judgement:** Tool SET selection is deterministic and the budget (6-8) is actually enforced — the architecture has the right backbone; but full-cap 8-tool profiles, fragile first-match-wins keyword routing, String operation arguments and the absence of in-turn recovery from a wrong profile produce silent capability gaps and hallucination in a small model.


**Current state.** The tool set is chosen DETERMINISTICALLY, not by the model: `intentProfile` matches the lower-cased text of the question against keyword lists in 8 languages and returns one of 4 profiles (ModelService.swift:527-556). The profiles and their real tool counts: everyday = 8 tools (Calendar, Reminder, Contact, Search, Calc, Time, Watch, Code; :280-290), document = 8 (Create, Read, Edit, Calendar, Reminder, Search, Calc, Time; :301-311), search = 3 (web_search, Calc, Time; :320-325), connection = the first 6 MCP + Calc + Time = at most 8 (:329-333, cap `mcpToolCap = 6`, :121). Within a profile the MODEL picks 1-of-N. The precedence is first-match-wins: attached-document lock > everyday traces > document traces > connection > search > sticky current (:530-555). The next turn's signal is read from the chip icons rather than from the model's text (:590-593) — that direction is closed to hallucination. The 6-8 tool budget is genuinely enforced; but everyday/document sit exactly at the cap (8) and the code's own comment admits the cap is "BEING STRAINED" and that `time` will be dropped if the device measurement comes out poorly (:276-279).


**Strengths:**

- The tool SET is chosen deterministically; the small model does not choose which tools are on the table, it only picks one from a narrow set — the wrong-set error surface is entirely closed (ModelService.swift:527-556).
- The tool budget (6-8) is actually enforced: no profile exceeds 8, and on the MCP side the cap is applied BEFORE translation, coming down to 6 even on a 200-tool server (:1037, :121).
- The off-device profiles (search, connection) exclude personal-data tools STRUCTURALLY: if the tool is not in the session the model cannot write the data into an argument even by accident (:313-333).
- The next-turn routing signal is read from the chip icon the tool dropped, not from text the model produced — a deterministic channel closed to hallucination for a follow-up question ("and tomorrow?") (:587-593).
- To avoid needless session rebuilds the profile does not change if the current one satisfies the request; a profile switch preserves the transcript and happens in one go (:524-526, :780).
- Tool arguments are typed with @Generable/@Guide; the model does not produce free text to be parsed (TacetTool.swift:5-7).

### A.3 Tool schemas & descriptions (@Generable/@Guide)

**Summary judgement:** Constrained decoding and single-string tools are a solid foundation; but the native tools' discriminator/format fields being plain Strings instead of real enums, together with the native/English language mixing, leave open exactly the concrete hallucination surfaces a 3B model will stumble on most often.


**Current state.** All native tools are defined type-safely with the FoundationModels `Tool` + `@Generable`/`@Guide`; the model does not produce free text to be parsed, constrained decoding is in place (TacetTool.swift:6-7). Most arguments are a SINGLE required string: Calc `expression` (CalcTool.swift:20-23), Contact `name` (ContactTool.swift:12-15), Search `keyword` (SearchNotesTool.swift:18-21), WebSearch `query` (WebSearchTool.swift:30-33) — ideal simplicity for a small model. The descriptions are in English and most carry a concrete example ("e.g. 'istanbul weather tomorrow'"), a deliberate choice (Router.swift:8-10, report §5.4: an English instruction works better on a small model). However the discriminator and format fields are NOT real enums; they are given as plain `String` + the advice "use these exact values" and resolved on the code side by fuzzy matching such as `.lowercased().contains("add")` (TimeTool.swift:21, CalendarTool.swift:19-30, ReminderTool.swift:176,185-186, CreateDocumentTool.swift:24). Calendar/Reminder fold two actions (read/write) into a single tool with an `action` string; conditionally-required fields are described only in prose. The number of active tools per profile is kept at 3-8 (ModelService.swift:289,310,324,332). On the MCP side the schema is translated at runtime: a depth limit of 4, a tool that does not flatten is skipped, a count cap of 6, and the tool description is summarised to 160 characters (MCPTool.swift:365-424, ConnectionService.swift:310-327).


**Strengths:**

- Constrained decoding: the model cannot produce an argument that violates the schema; there is no free-text parsing anywhere (TacetTool.swift:6-7). Even in MCP, Arguments=GeneratedContent is locked to the schema (MCPTool.swift:122-124).
- Most tools carry a single required string field (Calc/Contact/Search/WebSearch) — the safest schema shape for a 3B model; a single slot to fill, minimum hallucination surface.
- The @Guide descriptions are short and nearly all contain a concrete example (TimeTool.swift:21, CalcTool.swift:22, WebSearchTool.swift:31), which makes it easier for the model to imitate the right form.
- The descriptions are in English — a small on-device model's instruction-following is stronger in English (Router.swift:8-10) and this was chosen by eval.
- The MCP schema is defensive against a small model: a depth limit of 4 (MCPTool.swift:368), a tool that does not flatten is skipped, a count cap of 6 (ModelService.swift:121), the description is trimmed to 160 characters (ConnectionService.swift:314-326) — the window is not filled by a single tool.
- MCP enums are translated into a real constrained option list (MCPTool.swift:406-412 anyOf): the model cannot step outside the list.
- Thanks to the profile lock the model sees at most 8 tools at a time; tool crowding is deliberately bounded for a small model (ModelService.swift:289,310,324).

### A.4 MCP bridge & dynamic tool load

**Summary judgement:** The tool count cap, single-connection selection, summarisation and depth filter are solidly built for a small model; the real gap is that schema WIDTH is unbounded and that the 6-tool budget is filled blindly by server order rather than by relevance.


**Current state.** Tools arriving from the remote MCP server are filtered by a four-layer cap: `maxTools = 200` and a `maxPages = 20` pagination limit in the client (MCPClient.swift:105-109,215), `mcpToolCap = 6` in the profile (ModelService.swift:121), only a SINGLE connection is selected at a time (ModelService.swift:145-149), and the cap is applied BEFORE schema translation (`.prefix(cap)`, ModelService.swift:1037). So from a server returning 30 tools, at most 6 remote tools + Calc + Time = 8 tools reach the model; the small model is never drowned in 30 tools. Definition summarisation is GENUINELY applied: at add time every description is reduced by the on-device model to ~20 words/160 characters and cached in `toolSummaries` (ConnectionService.swift:309-327), and only this summary enters the session (MCPTool.swift:158). Schema depth is limited by `depthLimit = 4`, `anyOf/oneOf/allOf/$ref` are rejected, and a tool that cannot be translated is not silently swallowed but listed as "unsupported" (MCPTool.swift:327,368; ConnectionService.swift:345-366). The dirty-session approval gate is kept in code and the model cannot see the flag (ToolExecutor.swift:50-53,87-112), and the connection profile structurally leaves personal-data tools out (ModelService.swift:327-333).


**Strengths:**

- The tool count cap is multi-layered and applied BEFORE translation: a server with 30 (or even 200) tools never gives the model more than 6 remote tools (ModelService.swift:1037, MCPClient.swift:109, ModelService.swift:121); because a single connection is selected, multiple servers do not inflate the budget either (ModelService.swift:145-149).
- Definition summarisation actually exists and is cached: a raw 100-500 token description never enters the model, a summary reduced to ~20 words does (ConnectionService.swift:314-327, MCPTool.swift:157-158) — in a 4096 window one tool's definition does not fill the window.
- Schema depth is bounded deterministically (remaining:4) and union/recursion types (anyOf/oneOf/allOf/$ref) are rejected with the tool skipped; a deep tree the small model could not fill never enters the session (ConnectionService.swift:350-366, MCPTool.swift:365-424).
- Thanks to constrained decoding the model cannot produce an argument that violates the schema; the schema is built at runtime without a compile-time type (MCPTool.swift:9,119-124).
- The approval gate is in code, not in the model; the denial cache (deniedSources) structurally prevents the model from entering an insistence loop (ToolExecutor.swift:58,88-92,108). By never containing personal-data tools, the connection profile makes single-step leakage impossible (ModelService.swift:327-333).

### A.5 Skill/guidance injection (progressive disclosure)

**Summary judgement:** Single-skill progressive disclosure and end-of-prompt injection are the right instincts; but the 700-character blind truncation throwing away the vital example/rules, word-boundary-less substring matching loading the wrong skill, and the injection being disconnected from the profile/tool set make the design unreliable for a small model.


**Current state.** The skill layer imitates Claude's SKILL.md logic: `Skills/*.md` are loaded as frontmatter (name + triggers) + body (SkillStore.swift:97-131), and user skills are kept in SwiftData (UserSkill.swift). On every turn the SINGLE skill that best fits the message is chosen (SkillStore.swift:64-74) and attached ONCE to that session — not to the system instruction but to that turn's prompt (ModelService.swift:382-389, 791). The injection is wrapped in a `<guidance name=...>` fence plus a "never mention/summarise" line, and the body is limited to 700 characters (SkillStore.swift:78-93); a user skill's body is additionally limited to 500 characters (UserSkill.swift:16). The match score is the sum of the LENGTHS of the matching triggers (not the count), so a specific phrase such as "as a table" beats "table" (SkillStore.swift:64-74). Matching is a raw substring scan via `s.contains($1)` (SkillStore.swift:68). Profile/tool selection, in contrast, is done by a COMPLETELY SEPARATE keyword system (intentProfile + everydayTraces/documentTraces/searchTraces, ModelService.swift:527-657), and skill injection runs independently of that profile.


**Strengths:**

- The basic progressive-disclosure decision is right: injecting only 1 skill, 1 time, rather than embedding all 10 skills into the instruction, is the correct instinct for a 4096 window (SkillStore.swift:5-9, ModelService.swift:344-350).
- Placing the skill guide not in the fixed instruction but in that turn's prompt and IMMEDIATELY BEFORE the question is a deliberate, measurement-based choice exploiting last-block weight in a small model (ModelService.swift:346-367).
- Length-weighted scoring (rather than count) resolves a genuine ambiguity: 'show this as a table' → read-document, 'make a table' → create-document; the rationale is explicit in the code (SkillStore.swift:57-63).
- The skill bodies are in the imperative, name the tool BY NAME and show a concrete `tool(arg)` example (code.md:17, web-page.md:17) — the right form for pushing the model to call a tool rather than to 'narrate'.
- A hard 500-character cap on the user's own skill is enforced in the UI with a live counter (SkillBoard.swift:250,341-345), so the user cannot silently inflate the budget.


**Weaknesses:**

| Weakness | Evidence | Small-model impact |
|---|---|---|
| **[CRITICAL]** The 700-character truncation throws the EXAMPLE and RULE sections (the hallucination fences) off the end of the 5 longest skills | SkillStore.swift:78-85 cuts the body to 700 at the last line boundary. ### A.6 Structured output & parsing fragility

**Summary judgement:** The deterministic guarantees (code sandbox, HTML verification, roundtrip test) are strong; but table parsing is bound to one rigid form and produces silent loss/garbage files on the error path — in the small model's most likely deviations (a missing separator, no outer pipe, a cut stream) the structure breaks invisibly.


**Current state.** The model gives structured output through two channels: (a) a markdown table embedded in the chat text, (b) markdown as a tool argument (create_document/edit content). Both are bound to the same parser: Table.markdownTables requires the row to start with "\|", the next line to start with "\|" and contain "-" (the separator), and at least one data row (Table.swift:56-84). In chat a table is rendered only once generation FINISHES; during streaming plain text is shown so that a half table does not flicker (TacetReply.swift:147-164). Code output is deterministic: if there is no print, the value of the last expression counts as the output (CodeEngine.swift:96-98) and there are at most 2 executions per turn, then error_final (RunCodeTool.swift:62-68). On the HTML side the model produces only markdown, the scaffold+style are embedded, and the generated page is verified in an off-screen WKWebView; if it fails the file is deleted and "simplify and try once more" is returned to the model (HtmlEngine.swift:5-12, CreateDocumentTool.swift:65-77). The format pressure on the model is explicit: "To show a table, output the markdown table rows (\| … \|) themselves — a sentence instead of the rows is a failure" (Router.swift:40-41).


**Strengths:**

- During streaming a table is NOT rendered, plain text is shown (TacetReply.swift:147-152) — the small model's half table flowing token by token does not flicker on screen; the snap happens once, at the end.
- The hallucination surface in code execution is closed deterministically: the model cannot claim a result, a tool runs it; if there is no print the last expression value is the fallback (CodeEngine.swift:96-98); the attempt counter makes the engine refuse to run at all on the 3rd call (RunCodeTool.swift:60-68).
- The HTML scaffold+CSS are embedded in the app; the model never sees the template and the 4096 window stays for content (HtmlEngine.swift:5-12). The generated page is verified deterministically and is not presented to the user if broken (PageVerifier.swift, CreateDocumentTool.swift:65-77).
- There is tolerance for ragged (missing-cell) rows: both in markdown production and in display, the cell count is padded against the header (Table.swift:103-105, ChatTable.swift:30, HtmlEngine.swift:190-192).
- The table roundtrip (markdown ↔ Table) is designed symmetrically and verified in SelfTest (SelfTest.swift:87-94); read_document truncates the table to 30 rows and returns markdown to the model, protecting the budget (ReadDocumentTool.swift:43, Table.swift:47-52).
- The create_document format field is free text but is matched tolerantly by DocumentFormat(userText:); even if 'python' is said the code is solved in JS (RunCodeTool.swift:70) — an enum miss does not turn into a crash.

|---|---|---|
| **[High]** The table detection gate is too strict; common small-model deviations fall through to raw pipe text | TacetReply.swift:190 `if s.hasPrefix("\|"), next.hasPrefix("\|"), next.contains("-")` and Table.swift:63-65 look for the same triple condition. | A ~3B model frequently produces a markdown table without outer pipes ('Coffee \| Price') or without a separator row. ### A.7 Bulk data offload & the 4096 bypass (DataStore + sourceRef)

**Summary judgement:** The offload architecture is deterministically solid in its channel split and monotonic reference, but the chain's most fragile link from a small model's point of view — carrying the reference correctly across turns — has been left to the prompt, and an unresolvable ref silently ends as 'success' with an empty/incomplete document; without fixing that single point the pattern is not reliable on a small model.


**Current state.** Bulk device/document data is carried over DataStore without passing through the model: the source tool stores the Table with `put` and produces a short reference ID (DataStore.swift:23-28), and the producing tool CreateDocumentTool pulls the full table from the store with `get(ref)` (CreateDocumentTool.swift:46). The text RETURNED to the model and the RAW output in the chip detail are deterministically separate: the tool contract returns only `returnedToModel` to the model, `rawOutput` stays in the chip (TacetTool.swift:41, ToolOutcome:84-92). Source tools give the model only a truncated preview + a ref: Calendar a summary of the first 10 events + `data_ref` (CalendarTool.swift:124-148, the trigger rows.count>1 at line 67), Reminder the first 10 + `data_ref` (ReminderTool.swift:322-352), WebSearch a ≤~300 token list + `data_ref`, without full URLs (WebSearchClient.swift:235-253, 656), MCP/connection output above 800 characters the last 30 lines + `sourceRef` (ConnectionService.swift:418-445). But read_document is OUTSIDE this pattern: it dumps the content it read straight to the model — a 30-row markdown table or plain text, truncated to 1500 characters (ReadDocumentTool.swift:43-44). ContactTool has no store channel at all, it only summarises the first 5 contacts (ContactTool.swift:80-87).


**Strengths:**

- The channel split is DETERMINISTIC and in a single place: whatever the tool returns, only `returnedToModel` goes to the model and `rawOutput` stays in the chip (TacetTool.swift:41). The model never sees the full bulk data; this rests on code, not on the model's good intentions.
- The reference generator is monotonic: `clear()` empties the store but DELIBERATELY does not reset the counter (DataStore.swift:40-48). The risk of regenerating 'calendar-1' in a new chat and colliding with an old reference / producing a document from another chat's data is entirely closed — even if the small model remembers an old ref, the data does not mix.
- `get()` matches tolerantly: if the model adds quotes/spaces to the ref it cleans them and still finds it (DataStore.swift:33). It absorbs part of the small model's typical dirt.
- The summaries going to the model are genuinely bounded: previews with prefix(10)/prefix(5), the web summary with a 200-character-per-line cap + a total of ≤~300 tokens, and the FULL URL does not go to the model (WebSearchClient.swift:232-253) — the hallucinated-link and 'X results found → invent a number' surface is deliberately narrowed (comment 244-249).
- Storing is thresholded: a single-record read does not produce a ref (count>1 gates), and MCP output under 800 characters passes through as-is (ConnectionService.swift:420) — no needless ref is produced to confuse the model.

### A.8 Error/retry/cancellation semantics (small-model fitness)

**Summary judgement:** Cancellation and LOCAL side-effect retry semantics are flag-based and soundly designed for a small model; but remote (MCP) writes falling entirely outside retry protection, and error recovery being blind to turn cancellation, are critical gaps that can produce a double external side effect and an invisible race on a fragile 3B model.


**Current state.** A turn's outcome is read from explicit flags, not from TEXT: `ReplyOutcome` (`isError`, `retryable`, `isTransient`) is filled by the service and the UI does no string comparison (ModelService.swift:41-53; ChatView.swift:358-364). Retry safety is protected by a single sticky boolean: when a tool reports `.written`, `ToolExecutor.worldChanged` becomes true (ToolExecutor.swift:140,163), and if `recoverFromError` sees this at the very top it blocks the retry entirely and returns only an error bubble (ModelService.swift:817-821); if there is no side effect, an overflow (`exceededContextWindowSize`) is summarised and retried once, and other transient errors are retried once with a fresh session (ModelService.swift:831-853). There is no retry on guardrail and language errors (ModelService.swift:822-830). Cancellation is not counted as an error: the stream inside `swallowStream` runs in a separate Task, `stop()` cancels it, `CancellationError` is caught and the `streamingText` accumulated up to that point is returned like normal text (ModelService.swift:856-895). The cancellation race is handled with `generationNo`: `stop()` advances the counter and immediately sets `generating` to false; the `replyOutcome` defer, with the condition `if generationNo == myTurn`, prevents an old turn's late defer from dropping the new turn's flag (ModelService.swift:689-706,752-757).


**Strengths:**

- Error detection in the UI is done by flag INSTEAD of string matching; the bubble does not silently die when an error string changes (ModelService.swift:41-53) — the right architectural choice against a small model's variable output.
- Cancellation and a real error are cleanly separated: cancellation preserves `streamingText` and returns normally, and triggers no retry (ModelService.swift:891-894); when the user presses 'stop' the half reply stays on screen.
- `generationNo` + the defer guard protect the new turn's `generating` flag in the race of pressing 'stop' during a long turn and immediately sending a new request (ModelService.swift:700,757) — a race met often in practice during the small model's minutes-long turns.
- `stop()` sets `generating` to false IMMEDIATELY; it does not wait for the stream to die down, so the send button does not freeze on the stop icon and reject a new request (ModelService.swift:697-701).
- The retry lock against repeating a local side effect is correct: if a writing tool ran, `recoverFromError` neither retries automatically nor offers the 'try again' button (`retryable=false`) (ModelService.swift:817-821; ChatView.swift:252).


**Weaknesses:**

| Weakness | Evidence | Small-model impact |
|---|---|---|

### A.9 Evaluation & self-test coverage

**Summary judgement:** The deterministic fences are automatically tested at an exemplary level, but the small model's genuinely fragile behaviour (language anchor, argument correctness, format compliance) has either been left to the eye or abandoned to single-sample runs bound to no gate — so the self-test does not, in practice, protect the model's riskiest surface against regression.


**Current state.** The self-test is split across three separate DEBUG command-line runners, all triggered by hand (TacetApp.swift:16-24: `--selftest`, `--test`, `--language`). (1) SelfTest.swift + SelfTestCases.swift are a pure assertion suite REQUIRING no model/network: SelfTestLedger produces real asserts with an error counter (SelfTestCases.swift:39-53) and statically scans the memory filters, deduplication, the injection budget, the approval gate and the network monopoly. (2) Evaluation.swift runs the REAL on-device model over ~28 chat cases plus memory/timeline/web blocks; it reads the score from the chip icon (Evaluation.swift:124 `traces.map(\.icon)`) — so it genuinely exercises the model's tool selection, but it writes the result only to a text file under Caches (lines 190-192), with no threshold/exit code at all. (3) LanguageTest.swift runs 9 languages × 6 cases on the real model but only counts the tool icon; it leaves the reply language "to the eye" (LanguageTest.swift:113-114). The project has no XCTest target, no CI file and no sampling/temperature control at all (grep empty; ModelService.swift:867 `streamResponse(to: question)` takes no options).


**Strengths:**

- The deterministic guarantees are asserted generously and genuinely: SelfTestCases exercises the memory filters, deduplication, 2 notes per call / a cap of 50, the injection budget and the approval gate over pure functions (SelfTestCases.swift:96-205, 673-762) — these are the fences around the small model that 'must hold even without a model', and they produce real pass/fail.
- An acceptance criterion suited to small-model reality: the memory block separates 'false positive = fail' from 'miss = quality warning' (Evaluation.swift:203-231, 321-344); missing a correct note does not fail the run, inventing one does.
- The hallucination surface is targeted directly: in world-knowledge/weather cases replyMustNotContain looks for 'Paris'/'degrees' (Evaluation.swift:39-40), and in web-non-invention an honesty pattern is required (lines 520-533).
- Tool verification rests on the tool's own trace (ToolTrace/chip) rather than on the model's narration (ToolTrace.swift:29-53); because the model cannot invent the chip text, the 'was the tool called' signal is reliable.
- The token budget is locked statically: it is asserted that the worst-case sum of skill + memory stays at ~1600 characters (SelfTestCases.swift:296-303) — a measurement that directly protects the 4096 window.
- The static network-monopoly scan (SelfTestCases.swift:773-823) locks the question 'what leaves the device' against regression; if the source tree cannot be read it does not pass silently but fails explicitly.

| **[CRITICAL]** Real-model behaviour tests are bound to no automatic gate; run-and-eyeball by hand | Evaluation.swift:190-192 writes the result to a file and says `print("EVAL finished")`, with no threshold/exit; LanguageTest.swift:126 is the same; TacetApp.swift:19-23 is triggered only by a DEBUG command argument; the project has no XCTest target/CI (find empty). | This is exactly the 'the mechanism gets built but is never wired into production' regression pattern described in the memo. | Priority | Title | Rationale | Draft approach |
|---|---|---|---|
| P0 | Bind the model-behaviour eval to an automatic gate with a threshold and an exit code | Weakness #1 (critical) is the regression pattern the memo fears most: the behaviour test exists but breaks nothing. In a small model, tool selection/language/format are the most likely regression points and they are exactly the layer left to run-and-eyeball. | Move Evaluation and LanguageTest from 'write to a file + eyeball' to a structure producing a clear total ratio + threshold; on failure give a non-zero exit so that a UI-test target/simulator run breaks the build in CI. To resolve the tension of real calendar/contact data, run the eval over fixed, injected FAKE fixtures — the memory block already uses an in-memory ModelContainer (Evaluation.swift:296-311); extend the same pattern to calendar/contact/note to make it deterministic and CI-safe. Then a 'green eval' is bound to a gate rather than to a human remembering. |
| P0 | Suppress nondeterminism: lowest temperature + an N-run majority ratio per case | Weakness #2: a single-sample, optionless run gives a noisy signal; before setting a threshold the signal must be stable, otherwise CI becomes flaky and gets disabled. | In the eval run, pass the most deterministic sampling possible (lowest temperature / greedy) to the model via GenerationOptions; additionally run every behaviour case N times (e.g. 5), report the pass RATIO and define the threshold over the ratio (e.g. pass at ≥4/5). That separates a real regression from sampling noise and produces an actionable metric such as 'this case is 60% stable' — a binary pass/fail is misleading given the small model's nature. |
| P1 | Assert the language anchor automatically with on-device language detection | Weakness #3: tool selection is measured across 9 languages while the genuinely fragile behaviour (the reply language) is left to the eye; language drift is the small model's signature error and is currently never caught. | Run a network-free, on-device language recogniser (NaturalLanguage/NLLanguageRecognizer) over every reply; fail the case if the dominant language does not match the expected one. Make the critical scenario a separate case: let the tool return a result in a foreign language to a native-language question, and require the reply to stay in the user's language — that is the only thing that would actually exercise the instruction's 'tool results may be in another language, restate in the user's language' rule (Router.swift:30-32). |
| P1 | Exercise argument and result correctness through rawInput/rawOutput | Weakness #4: the difference between 'the tool was called' and 'the tool was called with the right argument' is the most expensive error class in a small model (a wrong time, an inverted percentage) and is currently entirely invisible. | Use the existing ToolTrace.rawInput/rawOutput fields: in the calc cases look for the expected numeric result (1000/135/200) in the tool output or in the reply text; in calendar-add verify that rawInput contains 14:00 and 'meeting', and in reminder 18:00. Generalise the '1060' content check in code-prime (Evaluation.swift:80) to the other calc/time/reminder cases. This makes icon-only scoring argument-aware. |
| P2 | Turn live format compliance (producing table rows) into an assertion | Weakness #5: the instruction's most fragile format rule is tested only on the static engine side; whether the model actually prints \| … \| is never measured. | In the read-document/edit and 'show the table' cases, look for a genuine pipe row (a line containing at least 2 '\|') in the reply text; fail if absent. That automatically catches the 'I showed the table but did not print the rows' error (the behaviour forbidden by Router.swift:41-43). |
| P2 | Tighten the weak assertions and wire up the dead currentTime() | Weakness #6: assertions such as `":"` produce false greens, and the dead code shows the test's intent has rusted; cheap cleanup that yields real coverage. | Bind the time-clock case to the real clock prefix with `replyMustContain: currentTime()` (which also brings the dead code into play) and, in general, make every replyMustContain assertion more specific. Review that an assertion is not a substring 'findable in any reply'; otherwise the case is providing no protection. |
